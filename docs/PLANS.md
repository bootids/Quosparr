# Execution Planning Policy

This repository-local policy governs task plans; it is not a roadmap or an unmodified upstream snapshot. Choose planning depth by task needs, not by model branding.

## Choose the smallest useful plan

Use task risk, uncertainty, coordination needs, and recovery needs to choose the level. Do not choose the level solely by model name, estimated duration, or number of changed files.

- **Direct work:** For a clear, local, reversible, low-risk change, inspect the relevant context, implement, and perform proportionate verification. No durable ExecPlan is required.
- **Lightweight plan:** For a bounded change that benefits from sequencing, record the goal, relevant context, a few implementation steps, and acceptance checks. Session notes are sufficient unless the work must survive a handoff or interruption.
- **Durable ExecPlan:** Use one for work spanning sessions or contributors, consequential interfaces, significant uncertainty, broad refactors, risky migrations, or other changes that need an auditable recovery point. Escalate a lightweight plan when new information makes this necessary.

Look for an existing plan for the same work before creating a competing plan. Reuse or explicitly supersede it. Create plan directories when needed rather than requiring empty directories in every repository.

## Durable plans and their location

A task chain is one ID with one versioned directory and one unversioned directory. The versioned part holds the durable record; the unversioned part holds session handoff and working outputs.

```text
docs/exec-plans/<id>/          versioned
  PLAN.md                          required, fixed name
  EXPLORATION.md                   required when kind: exploration
  recipe/                          optional small texts: prompts, scripts, parameters
docs/exec-plans/INDEX.md       registry; generated by the registry tool, do not edit by hand
out/<id>/                          unversioned; the repository must ignore out/
  HANDOFF.md                       chain-specific session handoff, overwritten, at most one page
  <NN>-<dispatch-name>/            one directory per dispatch: TASK, REPORT, rework rounds, logs, artifacts
out/scratch/                       purely temporary
```

The chain ID is `YYYYMMDD-<slug>`, where the slug matches `[a-z0-9]+(-[a-z0-9]+)*` and the whole ID is at most 48 characters. The directory name must equal the ID. Use a new chain for a new subtopic and link it with `parent:`; do not append an unrelated subtopic to an existing chain. Mark replaced work with `superseded_by:` instead of deleting it.

Status lives only in the PLAN.md frontmatter: `draft | active | blocked | done | superseded | cancelled`. Do not move directories between `active/` and `completed/`; there is no second location. The old `active/` and `completed/` subdirectories are legacy layout: do not create them, do not error on them, and do not migrate them automatically.

Do not put TASK, REPORT, rework, log, or HANDOFF files in a plan directory. Those belong in `out/<id>/`; the plan directory holds only the durable plan, exploration record, and recipe material.

Use ordinary Markdown. Headings, lists, tables, and code blocks are all allowed when they improve clarity. A Markdown file does not need an outer code fence. Do not duplicate the same instructions across milestones, edit lists, and command transcripts.

## PLAN.md frontmatter

Every PLAN.md begins with YAML frontmatter between `---` lines. Required keys: `id`, `title`, `status`, `kind`, `created`, `updated`. Optional keys: `parent`, `superseded_by`, and `refs` (a list of backlog or decision IDs). `kind` is `plan` or `exploration`. Dates use `YYYY-MM-DD`, and `created` must not be later than `updated`.

```yaml
---
id: 20261017-example-chain
title: Outcome-oriented title
status: draft
kind: plan
created: 2026-10-17
updated: 2026-10-17
# parent: 20261001-parent-chain
# superseded_by: 20261020-replacement-chain
# refs: [B-12, D-7]
---
```

`id` must equal the chain directory name. Use `parent` for a genuinely separate subtopic; do not use it to keep a single chain alive indefinitely. `superseded_by` is required when `status: superseded`.

## Required content

Every durable ExecPlan must provide the following information, using the skeleton below or an equivalent clear structure.

**Outcome and acceptance.** State the requested observable result, non-goals, and the checks that distinguish success from failure. Separate engineering acceptance from subjective review where necessary. Do not silently reduce scope or weaken acceptance to make the task appear complete.

**Relevant context and constraints.** Identify the repository-relative paths, existing contracts, environment requirements, and project-specific terms needed for this work. Summarize critical constraints inline. Link to maintained repository documents instead of copying them wholesale. External sources may support the plan, but indispensable knowledge must have a usable local summary or a repository-accessible pinned reference.

**Milestones.** Organize work into meaningful, verifiable increments. Specify observable behavior and contractual boundaries. Prescribe internal implementation details only when they are actual constraints or established decisions; label candidates and untested approaches as provisional. If feasibility is unknown, start with a bounded experiment and explicit criteria for choosing the next approach.

**Current state and next action.** Record completed and remaining work, important modifications, blockers, and the next concrete action. Include the relevant revision or worktree context where available. A new contributor with the checkout and linked local documents should be able to recover without the previous chat.

**Decisions and open questions.** Record consequential decisions, rationale, and unresolved assumptions. Do not log every tool call or routine implementation choice. Mark assumptions as unverified until evidence resolves them.

**Validation and outcome.** Name the actual checks, relevant environment, expected behavior, and observed results. Separate planned checks from executed checks. Record remaining gaps and the final outcome.

## Task chains and session handoff

Before starting substantial work, select a chain to continue or create a new one. Start from `docs/exec-plans/INDEX.md` when it exists, and also inspect chain directories under `out/`; the index is a registry, not a substitute for reading a candidate's current state. Only one session may write a chain at a time. Work that needs no cross-session continuity or executor dispatch does not need a chain and may stay direct or lightweight.

Each chain has exactly one handoff at `out/<id>/HANDOFF.md`. Its first line is the fixed, untranslated marker `任务：<repository-directory-name>-<id>`; tooling parses this prefix, so do not translate or reformat it. The body records only the current state: goal, current status, next step, uncommitted files this chain owns, and key paths. Overwrite it; do not append a running log. Keep it to at most 60 lines (one page). Durable conclusions belong in PLAN.md or EXPLORATION.md, not in the handoff.

Write only your own chain's files. Shared registers such as INDEX.md and BACKLOG.md are generated by tools; do not hand-edit their generated blocks.

## Exploration records

Use `kind: exploration` when one goal is pursued through multiple candidate approaches and the path to the winner matters: visual variants, shader parameters, prompt rounds, algorithm choices, tuning runs. This differs from `research/` in the production layer, which records external material research rather than this repository's own experiments. A plan that merely contains uncertainty remains `kind: plan`.

An exploration chain also has EXPLORATION.md with these fixed sections:

- `## Question and decision criteria`
- `## Candidates` — table columns: ID, Approach, Status (`untried | trying | rejected | winner`), Why.
- `## Attempts` — append-only. Add one row immediately after the planner judges each round: #, Date, Candidate, Inputs, Prompt or script, Model·level or params, Output, Planner verdict, User verdict.
- `## Decision` — winner, date, who decided (aesthetic calls are settled by the user's final choice), and why. Link a `D-xxx` decision when the production layer is enabled.
- `## Recipe` — the reproducible winning path: When to use, Inputs, Steps, Exact prompts and parameters (files under `recipe/`), Acceptance, Known failures and why, Skill candidate (`yes | no`). This section is the future input for turning the work into a skill.

Rules for exploration chains:

- Inputs cited by Recipe and by specification documents must be versioned files or external asset-library entry IDs (for example Eagle); never `out/` paths.
- Copy the winning prompts and scripts, plus representative failed attempts, into `recipe/` when they are small text.
- Keep large binaries in `out/` or the asset library, and register their source in Attempts.
- Decide based on recorded attempts and the stated criteria, not memory. Do not rewrite history when a later attempt wins; mark earlier candidates `rejected` and keep their rows.

## Working outputs (out/)

`out/` must be listed in the repository `.gitignore`. It holds handoffs, dispatch directories, logs, generated images, and other working outputs that are not part of the durable record. `out/scratch/` is for purely temporary files.

Only the Attempts table and the evidence record in a PLAN.md may cite an `out/` path as a source. Any other versioned document that needs that material must first promote it: copy the small text into the repository, or register the binary in the external asset library and cite the entry ID. This keeps specifications usable after a fresh clone or on another machine.

## Execution and authority

Inspect the affected code, tests, and applicable repository guidance before treating a planned path, API, command, or assumption as fact. Read only the context relevant to the task, expanding as the task requires.

Proceed autonomously with authorized, reversible work within scope. A plan does not grant new permissions. Follow the user's authorization and repository policies for commits, pushes, deployments, engine upgrades, paid services, destructive changes, and access to sensitive data.

When a blocker is resolvable safely within scope, resolve it and continue. When a decision materially changes user-visible behavior, compatibility, cost, safety, or an agreed constraint, state the issue and obtain the required decision rather than guessing. Record the blocker and a resumable next action if execution must stop.

Never discard unrelated work to make the plan easier to execute. Keep experiments and temporary artifacts isolated and describe cleanup when it matters.

## Verification and evidence

Choose checks proportionate to the affected behavior and risk. Prefer the narrowest meaningful checks during iteration, followed by the broader checks required for acceptance. Do not rerun unrelated expensive suites without a reason; do not skip required gates merely because the model is capable.

For each important check, record its working directory, command or reproducible procedure, relevant inputs and environment, observed result, and evidence location. Use explicit statuses: `passed`, `failed`, `blocked`, `not run`, or `not applicable` with a reason.

Do not invent commands, test counts, outputs, benchmarks, or review results. Mark unverified commands as candidates until inspected or executed. Never count a skipped or blocked check as passed. Fix a test or update a baseline only when justified by the intended behavior, not simply to obtain a green result.

Compilation, a screenshot, a successful launch, and a functional test prove different things. State which property each check actually establishes. Large logs, videos, and profiles may live in an artifact store; preserve stable references, provenance, and any reproduction instructions the next contributor needs.

## Checkpoints and recovery

Update durable state after a meaningful milestone, a material discovery or change of direction, and before a handoff or context reset. Keep the record concise; Git history already records textual edits.

At a checkpoint, make the current state, validation status, remaining uncertainty, and next action explicit. On resume, verify that the plan still matches the current checkout and environment before continuing. Do not assume previously recorded results establish correctness for newly changed code.

Include rollback, backup, compatibility, and retry procedures when the operation warrants them. Safe recovery must preserve unrelated user changes and data. For irreversible operations, establish the required authorization and safeguards before execution.

## Conditional extensions

Add only the sections required by the task.

**Data and compatibility changes:** Include migration scope, data ownership, compatibility expectations, backup or restore procedures, and failure handling.

**Game and interactive work:** Include the relevant engine/toolchain, target platform, reproducible scene or scenario, starting state or seed where applicable, and input sequence. Distinguish logic, asset integrity, visual/audio behavior, performance, export/build, and human playtesting. Use suitable hardware and renderer conditions for performance claims. A headless or software-rendered check must not be presented as proof of target-device visual quality, audio behavior, frame rate, or game feel.

**Parallel work:** Define work ownership, shared interfaces, dependency order, integration checks, and an integration owner. Avoid concurrent edits to the same plan; use separate chains with `parent:` links or checkpoint reports where necessary. Do not introduce multiple agents by default.
